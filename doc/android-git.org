#+title: org-slipbox Android Git Transport

* Scope

The Android Git transport clones public HTTPS repositories and fetches public or
authenticated GitHub repositories without a Git executable on the device. It is
read-only: it creates and updates a bare object store and exposes no push or
remote-write operation. Exact fetched revisions can then be materialized into
immutable source-owned candidate snapshots. A source-scoped coordinator now
recovers the generation store, fetches, derives exact changed-file inventories,
materializes, stages the index and publishes one coherent generation. The
Compose connection flow drives that path for first import and activates the
Rust-owned catalog only after reopening the exact published generation.
WorkManager supplies the constrained source-scoped scheduling boundary for
subsequent refreshes.

The object transport and immutable source views are implemented in
=slipbox-git=; =slipbox-sync= owns staged index construction, refresh
coordination and generation publication. =slipbox-android= owns the native
boundary; versioned transport documents stay in =slipbox-rpc=. Kotlin obtains a
current credential from
=CredentialRenewalOwner=, copies it into a one-call byte array, clears that
array after JNI returns, and never puts it in request JSON.

* Dependency And Compatibility Contract

The workspace pins =gix 0.87.1= with default features disabled and only
=blocking-http-transport-reqwest-rust-tls= and =sha1= enabled. This retains the
workspace's Rust 1.85 MSRV. Android builds use the separately pinned Rust 1.98.1
toolchain documented in [[file:android-native.org][android-native.org]].
The locked transport dependency closure declares no Rust requirement above
1.85 and is checked directly with =cargo +1.85.1 check -p gix --locked=.

Rustls verifies Android HTTPS peers through the platform trust manager. Cargo
selects =rustls-platform-verifier 0.7.1= and its
=rustls-platform-verifier-android 0.2.0= support crate. Gradle reads that support
version from =Cargo.lock=, resolves the matching =0.2.0= AAR from the verifier's
restricted Maven repository, and pins its dependency lock and SHA-256. JNI gives
the verifier an application context once before Git work; initialization failure
is a closed transport fault rather than a network attempt.

* Network And Storage Bounds

- Only credential-free =https://= remotes enter production. Redirects, HTTP,
  SSH, URL rewriting, credential helpers, hooks, filters and repository programs
  are disabled or unreachable. Tests alone admit loopback HTTP for a smart-HTTP
  fixture.
- A credential callback answers an authentication challenge for exactly one
  operation. Credentials are accepted only for canonical =github.com= HTTPS on
  its default port, never persisted, included in a URL or configuration, or
  copied into an exported diagnostic.
- One explicit branch refspec is fetched, tags are disabled, and each request is
  shallow at depth 256. Existing older objects are not expanded or pruned by a
  refresh.
- The destination is an absolute bounded path. A new clone is bare, and an
  existing destination must already be a usable object store. The transport
  reports only closed failure reasons, a disposition, the fetched object count
  and the selected revision.
- At most eight native operations are active. Their positive operation IDs are
  unique while active; cancellation signals the matching =AtomicBool=. The Rust
  API reports preparing, connecting, receiving and complete progress stages.

There is deliberately no push, commit, merge, checkout mutation or remote-write
API in this crate or JNI surface.

* Snapshot Materialization

Materialization reads an exact 40-character fetched commit identifier through
=gix='s object database. It does not invoke checkout, the Git executable, hooks,
credential helpers, clean or smudge filters, submodule commands, LFS helpers,
decryptors or any repository-provided program. Executable blobs that are
eligible content become mode-600 ordinary files.

Each candidate has this private layout:

#+begin_example
SNAPSHOT/
  snapshot.json
  content/
    REPOSITORY PATHS...
#+end_example

The manifest binds format version 1, source identity, revision, notes folder,
counts, byte size and bounded diagnostics. An existing destination is accepted
only when that ownership tuple matches exactly; another source or revision can
never replace it. A new candidate is built in a mode-700 sibling temporary
directory and renamed into place only after its content and manifest are
complete. Cancellation, storage failure, malformed objects and exhausted total
budgets remove the temporary candidate and do not touch any existing snapshot.
Publication remains the later coherent source/index generation boundary.

Plain UTF-8 =.org= files are admitted only below the selected notes folder.
PNG, JPEG, GIF, WebP and UTF-8 text assets are admitted anywhere within the
repository so a note can resolve a repository-contained =../assets/...= target.
No path can leave =content/=. Valid in-repository Git symlinks are resolved from
the committed tree and copied as ordinary files or directories; absolute,
escaping, missing and cyclic links are omitted with explicit diagnostics. The
snapshot never contains a filesystem symlink.

The production bounds are 100,000 inspected entries, 64 diagnostics, 1,024
bytes per repository-relative path, 64 tree levels, 8 MiB per Org file, 32 MiB
per asset and 512 MiB of materialized bytes. Commit, tree, attributes and
symlink objects have separate read-before-decode bounds. A caller may lower the
entry/file/total limits but cannot raise them.

Encrypted Org, invalid text encoding or format, per-file oversize, Git
submodules, unresolved LFS pointers and external filter declarations are left
out and named in the source-bound manifest. Files outside the supported note and
asset policy are not source inputs and are not copied. A diagnostic budget that
cannot name every exception fails the candidate rather than silently truncating
the report.

Android calls this operation through the versioned =nativeMaterialize= byte-array
boundary. It carries no credential and shares the bounded operation identity and
cancellation registry with clone/fetch. Kotlin refuses foreground execution and
checks the returned operation and revision before accepting the result.

* Revision Deltas

=slipbox-git= derives an initial or between-revision file inventory from exact
commit objects. It compares the same admitted view used by materialization, not
a checkout or provider comparison API: eligible Org files and assets are
included, unsupported inputs are omitted, and changes to a confined symlink
target are attributed to each materialized output path. The result separates
added, modified and deleted paths and supplies rename identity hints. Exact
content moves are detected for every file type; bounded token similarity adds
edited-rename hints for admitted text without writing an Org ID.

The comparison is source-bound and fail-closed. Both trees are validated in
full before a result is returned, missing or malformed required objects fail the
operation, and cancellation or an exhausted entry, byte, diagnostic or change
budget produces no partial delta. Rename inference has separate comparison,
fingerprint-token and similarity-step limits. If an inference limit is reached,
the exact added/deleted inventory remains complete and the result marks rename
detection as limited rather than presenting incomplete hints as complete.

A request for the same revision and notes-folder policy validates the commit and
selected folder, then returns an empty delta without walking or parsing the
corpus. Other comparisons use commit trees directly and never depend on a merge
base. History is reported separately as initial, same-revision, fast-forward,
rewind, divergent or incomplete, so branch changes, force pushes and shallow
missing ancestry do not change the file inventory semantics.

The production bounds are 100,000 output changes, 4,096 inspected ancestry
commits, 16,384 edited-rename candidate pairs, 65,536 fingerprint tokens and
1,000,000 similarity steps, in addition to the snapshot admission bounds.
Initial imports use an empty previous inventory. This Rust result is the input
to staged incremental indexing; no corpus inventory is transported through
Kotlin.

* Staged Indexes

=slipbox-sync= builds a candidate index in a private sibling temporary
directory and renames it into its immutable destination only after SQLite
verification, WAL checkpointing and completion-manifest persistence. The
manifest binds format version 1, source identity, current and previous
revisions, notes folder, index schema, final file/node/link counts, and the
number of parsed, removed and source-proven renamed Org paths. Reopening a
candidate verifies both the database and its recorded counts before accepting
it.

An initial import parses every Org path in the initial delta into a new current
schema. A later import uses SQLite's online-backup API to copy the previous
completed index coherently even when it has a WAL, removes deleted and
renamed-away paths through the dedicated removal operation, and parses and
file-syncs only added, modified and renamed-to Org paths from the new immutable
snapshot. Asset-only changes advance the candidate revision without invoking
the Org parser or modifying derived rows. Git has no file mtime, so repository
index rows use a deterministic zero mtime and therefore match a clean rebuild.
An Org rename also collapses earlier file-key aliases onto its current path.
Exact current keys always win, and aliases whose target was deleted are removed,
so a reading reference cannot drift onto a later, unrelated file.

No file-level update calls whole-root prune logic. Failure or cancellation can
only alter the temporary candidate; the completed base database and manifest
remain unchanged. A base manifest or database on another schema is refused as
an explicit rebuild requirement. Migration and rebuild remain background
choices for later orchestration rather than an implicit query or UI-path
fallback. Only a verified candidate enters the coherent-generation publication
boundary below.

* Generation Publication

=slipbox-sync= owns a version-1 store for one explicit source root. A version-3
published generation contains the complete snapshot directory, complete
staged-index directory and a manifest binding the complete initiating source
record, revision, notes folder, previous revision, snapshot counts, index schema
and index counts. The source record makes branch, folder, repository, account
and credential-reference provenance inspectable without storing a credential.
Publication moves both
verified candidates into a private sibling staging directory, seals and verifies
that generation, then atomically replaces =active-generation.json=. Source,
index and generation manifests remain separate evidence and must agree whenever
an active generation is opened.

Activation is compare-and-swap against the generation observed before refresh.
A stale publisher cannot replace a newer ready generation, while retrying a
completed activation is idempotent. Only the active-manifest rename changes what
new readers acquire. Cancellation or failure at source, index, generation-
manifest or pre-activation boundaries leaves the previous active manifest and
its files untouched.

A generation lease fixes a source identity, generation identity, revision,
content root and database for its lifetime. Existing leases continue to read
their old query rows, Org bytes and assets after a newer generation becomes
ready; new leases read the new generation. Content files are opened through the
lease with confined relative paths, so an already-open asset descriptor cannot
be retargeted by activation. No published-generation deletion is part of this
boundary.

Freshness is explicit data rather than an inference from directory contents. It
reports the newest fetched revision, the active ready revision and generation,
and an optional fetching, materializing, indexing or publishing state. A fetched
or in-flight revision is never presented as ready.

* Startup Recovery And Retention

The store uses mode-600 filesystem locks for publication, recovery and live
generation readers. The operating system releases them when a process dies, so
a killed importer or reader cannot leave a stale owner behind. Publication and
recovery are mutually exclusive; recovery also excludes new lease acquisition
while it decides retention. Every sealed generation records the active
generation its publisher observed. Recovery may therefore complete exactly one
verified interrupted publication only when that compare-and-swap precondition
still holds. Partial stages, incompatible index schemas and conflicting sealed
publications are never activated.

Before activation replaces the active manifest, it atomically records the
previous verified manifest as the retained generation. Startup validates the
active source, index, schema, counts and manifest agreement. If they are corrupt
or unusable, it restores the retained verified generation; if no verified
generation exists, readiness remains absent. Recovery returns typed, content-
free notices naming the required action: retry the import, rebuild the index,
refetch the source, free storage or release readers.

Snapshot and index candidates live only below the store's explicit
=candidates/= directory. Startup reclaims its abandoned contents and incomplete
publication stages. It also removes generations other than the active and
retained pair once no generation lease remains. A live reader delays removal;
an already-open asset descriptor remains bound to its original bytes. Storage
therefore stays bounded by the active and retained generations plus work held
by live readers, and an explicit caller-supplied free-space floor reports
pressure without deleting readable data.

* Source-Scoped Refresh Coordination

=slipbox-sync= admits at most one refresh flight for each source and at most
eight source flights process-wide. An overlapping request with the same source
import configuration coalesces and receives the first flight's terminal result;
it does not execute a second fetch or publication. A request with changed
repository, branch, notes folder, provider repository, account or credential
reference supersedes the old flight, waits for it to stop, and then starts under
the new complete source record. Relabeling alone does not invalidate derived
content.

One Rust-owned path performs recovery, credential-policy enforcement, Git fetch,
tree comparison, immutable materialization, staged incremental indexing and
compare-and-swap publication. If an incremental base requires a rebuild, that
same flight explicitly derives an initial inventory and stages a clean index;
Kotlin never parses Org or mutates source structure. A fetched revision becomes
ready only after the generation manifest carrying its source configuration is
atomically active.

Cancellation and configuration supersession share the transport's atomic flag
and are checked between stages and within bounded Git, snapshot and index work.
Activation has an explicit linearization boundary: pre-commit cancellation
prevents activation, while cancellation that loses to an already committed
generation returns false. A panicking leader settles coalesced waiters, releases
its source and operation slots, and leaves the JNI boundary to report the closed
panic reason.

The version-1 =nativeRefresh= request carries a positive operation identity, an
attempt number, the complete source record, and explicit sibling repository and
generation-store paths. A credential is a separate optional byte array. Kotlin
accepts one only when its renewal owner matches the source, provider, account
and credential reference, and clears the bytes after the native call. The
=nativeRefreshStatus= request carries only source identity and reads current or
last terminal state from memory, so offline startup and UI status never wait for
a token, network or filesystem.

Structured status distinguishes recovering, fetching, comparing,
materializing, indexing, publishing, ready, failed and cancelled; it carries
the initiating source record, progress units, and separate fetched/ready
revisions and ready generation.
Failures distinguish authorization, rate limiting, transient transport,
configuration, unsafe input, rebuild, storage, publication, supersession and
cancellation. Recovery advice is one of never, reauthorize, bounded backoff,
free storage or rebuild. Callers may make at most three attempts; transient
backoff is 30 seconds and then 120 seconds, with no automatic fourth attempt.

WorkManager persists only a bounded versioned source record and trigger; it
never persists an access token. Stable unique names provide one periodic and one
one-shot lane per source. Startup and manual triggers use the one-shot lane and
therefore coalesce before reaching Rust; any overlap that does reach Rust is
coalesced by the coordinator. Periodic and startup work require connected
network, non-low storage and non-low battery, while an explicit manual refresh
does not wait for battery-not-low. The worker resolves opaque source-owned
sibling repository/store paths below Android no-backup storage off the main
thread and acquires a private credential only for the blocking native call.
Stopping work cancels its active native operation. A changed import
configuration cancels the active flight and re-enqueues both lanes; source
removal cancels every work item carrying that source's tag.

The version-1 =nativeSourceCatalog= boundary loads, verifies and commits source
selection without moving source mutation into Kotlin. Its commit request carries
the catalog revision observed before import, the complete source record (a
credential reference only, never credential material), the private
generation-store path and the exact generation returned by refresh. Rust
acquires a generation lease and verifies source provenance before the catalog
save. Stale revisions, conflicting identities and unavailable or mismatched
generations are closed failures; no partial corpus becomes active.

* Qualification

=slipbox-git='s tests serve real Git smart HTTP through a loopback CGI fixture.
They cover clone, a subsequent update, an unchanged fetch, the exact shallow
history bound, branch-only refs, preflight and in-flight cancellation, cleanup,
closed errors and credential redaction. Host Git constructs and serves the
fixture; the library under test never invokes it.

Object-delta fixtures cover initial imports, additions, edits, deletions, exact
asset moves, edited note moves, unchanged revisions, rewinds, unrelated branch
roots, missing ancestry, missing objects and changes reached through committed
symlinks.

Staged-index fixtures compare an incremental candidate with a clean rebuild
across node and occurrence search, glossary rows, stale-row removal, backlinks,
forward links and stored relation counts. They also remove an unchanged file
from a test snapshot after delta derivation to prove file-level staging neither
parses it nor treats the changed-file set as a complete-root prune inventory.
Failure, cancellation, incompatible-schema and idempotent-completion fixtures
verify isolation and explicit rebuild behavior.

Publication fixtures hold activation before its atomic boundary while query,
document and asset readers run concurrently, then prove that old leases retain
the old generation and newly acquired leases read the new one. They inject
cancellation after source sealing, index sealing, generation-manifest sealing
and immediately before active-manifest replacement; every case preserves the
last ready generation. Freshness serialization, stale-writer rejection and
idempotent read-your-ready-generation behavior are contract-tested as well.

Recovery fixtures terminate a real publication subprocess at preparing,
source-sealed, index-sealed, manifest-sealed, activation and completion points,
then reopen the store. They prove partial first imports remain unreadable,
sealed work alone can finish, stale locks disappear with the process and an
existing corpus remains readable. Corrupt-active fallback, incompatible-schema
rebuild reporting, simulated storage pressure, abandoned-candidate reclamation,
leased-generation deferral, bounded retention and open-asset behavior are also
covered.

The focused Kotlin tests prove that a rotated credential is the byte sequence
given to the actual native-call seam, that its temporary byte array is then
cleared, that a foreign credential owner is refused before vault access, that a
429 retains rate-limit recovery policy, and that status lookup preserves
fetched/ready distinction without invoking refresh. Rust concurrency tests cover
coalescing, configuration supersession, cancellation/activation races, bounded
retry and panic cleanup. The APK build additionally proves the Android-only TLS
initializer, version-matched verifier AAR, JNI export inventory and both native
ABIs.

Work scheduling fixtures cover initial registration, relabel-only updates,
configuration replacement, exact source removal, bounded startup admission,
manual coalescing and oversized input refusal. Worker fixtures use injected
credential-free executors to cover operation ownership, storage refusal,
cancellation and bounded retry. Device tests instantiate the real Worker on the
supported API stack, inspect the actual network/storage/battery/backoff request
constraints and prove that stopping it reaches the active native-operation seam
without blocking the UI thread.

An explicit device journey proves the remaining network and filesystem path
against real GitHub. It clones this project's public repository without a
credential, materializes that exact revision in application-private storage,
feeds a locally supplied private credential through the production renewal owner into a
native authenticated clone, and repeats the authenticated fetch. The credential
is staged over standard input into an application-private mode-600 file, is
absent from instrumentation arguments and Git URLs, and is deleted before the
network result is published. The result document contains booleans only; it
contains no repository identity, revision, path or credential.

With an emulator or device already attached and the private token stored outside
the repository, run from the repository root:

#+begin_src bash
android/tools/git-smoke/live-git.sh EVIDENCE_DIRECTORY \
  "$HOME/sync/.env.local.github"
#+end_src

The second argument defaults to that path. This manual journey uses the token as
the result of a controlled refresh exchange so the production renewal-to-Git
handoff is exercised. It does not replace the separate device-flow and token
rotation qualifications in [[file:android-auth.org][android-auth.org]]. Evidence directories are local artifacts and
must not be committed.
