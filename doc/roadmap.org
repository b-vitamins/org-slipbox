#+title: org-slipbox Roadmap

* Purpose

This roadmap maps near-term release bands to the public model in
[[file:model.org][doc/model.org]]. It covers direction, not dates.

* Release Bucket Discipline

GitHub milestones are the literal upcoming release buckets. This roadmap names
release-band themes and exit signals; issue bodies carry the per-release cut
list.

Before opening or preparing a release:

- the next open GitHub milestone should match the near-term roadmap band
- `CHANGELOG.md` =Unreleased= should describe only actual unreleased changes
- release-prep commits should keep version metadata, README release text, and
  Emacs package headers consistent

* 0.13.x: Consolidation

Theme: make the project smaller and easier to reason about.

Focus:

- compact public ontology and command taxonomy
- README, roadmap, milestone, compatibility, and readiness docs cleaned up
  around the shared model
- `slipbox-core`, CLI, server handlers, benchmark harness, and test helpers
  split along product-domain seams
- no-behavior-change contract matrix kept green through refactors
- deliberate decisions for duplicate command affordances
- manpage-grade command help aligned with the taxonomy
- consolidation scorecard with line-count and term-count evidence

Exit signal:

- largest files are visibly smaller or mechanically split
- docs read as durable guidance rather than release notes
- CLI/RPC/JSON behavior is preserved except for reviewed aliases or
  deprecations
- public concepts map cleanly to Notes, Relations, Explorations, Reviews,
  Assets, and System

* 0.14.x: Read Contracts And Hardening

Theme: finish the consolidation line by tightening read semantics and internal
module boundaries before the stability push.

Focus:

- bounded source-read contracts and structured read/error payloads across the
  core, RPC, daemon-client, server, and CLI paths
- reusable Rust service operations shared by daemon handlers and other headless
  callers without duplicating CLI glue
- further module splitting of the daemon-client, CLI, and server handlers while
  preserving public API, RPC behavior, and JSON shapes
- a shared durable-JSON file-store for saved artifacts, packs, and review runs
- batched lookups, materialized backlink/forward-link counts, and SQLite write
  pragmas so large-corpus paths stay inside the performance envelopes
- root-relative path confinement across CLI, server, write, and query paths
- patch-line hardening for capture finalization, property-drawer layout, and
  partial indexed node metadata

Exit signal:

- read paths return bounded, structured payloads with contract-test coverage
- internal module boundaries are auditable without changing public contracts
- benchmark gates hold across query, indexing, write, workflow, review, and
  graph paths

* 0.15.x: Stability Prep

Theme: make release and compatibility claims verifiable before any `1.0`
candidate.

Focus:

- tracker, roadmap, changelog, and release metadata stay aligned
- CI benchmark smoke gates and release benchmark guards have documented roles
- bundled-SQLite and system-SQLite source builds are verified through the
  documented commands
- upgrade and index-rebuild behavior is documented for ordinary users
- public CLI JSON, JSONL, JSON-RPC, and durable-record contracts are audited
  against the model and compatibility policy

Exit signal:

- default-branch CI is green on the release-prep commit
- release metadata gate passes for the intended version
- build verification covers both bundled and system SQLite paths
- the `0.15.0` milestone is closed with no open compatibility or release
  hygiene issues

* 0.16.x: Glossary

Theme: introduce a first-class personal glossary as a new public bucket, built
entirely on the existing Org-as-truth and derived-index model.

Focus:

- a Glossary bucket owning glossary commands and spaced-repetition study, with a
  term modeled as an Org note that carries a `#+glossary:` marker
- SM-2 spaced-repetition schedule stored in the term's property drawer so it
  syncs and rebuilds with the notes rather than in a side store
- stemmed, diacritic-folded node search through an upgraded `node_fts`
  tokenizer, with search ranking kept internal
- glossary list, search, term, due, grade, and mark surfaces across the daemon,
  CLI, and Emacs
- an Emacs experience covering capture, definition lookup and peek, a cockpit
  glossary lens, and a card-at-a-time review buffer

Exit signal:

- a term participates fully in node search, backlinks, refs, and graph, and its
  SM-2 state survives a derived-index rebuild
- glossary contract, rebuild-survival, and benchmark gates are green
- no web UI, HTTP server, SSE hub, SPA, second database, separate sync
  mechanism, or MCP surface is introduced

* 0.17.x: Reading Surface

Theme: add a read-only web reading surface as a third front-end over Notes and
Glossary, the deliberate and bounded introduction of the web UI, HTTP server,
and SPA that the 0.16.x line explicitly deferred.

Focus:

- ranked note-content search as a third search concept beside node search and
  occurrence search, landing across core, store, RPC, server, daemon-client, and
  the CLI, and exposed on the reading API; it is a parallel path that leaves
  `node search` and the Emacs recall behavior unchanged, and the reading entry
  surface searches note bodies through it, showing each hit's matched excerpt
- a `slipbox-web` crate that bridges HTTP to a spawned `slipbox serve
  --read-only`, over the same daemon-client boundary Emacs and the CLI use,
  never an in-process service
- operation mutation classification hosted in `slipbox-rpc` beside the method
  constants, so read-only is a machine-checkable allowlist and the serve guard
  rejects any non-read-only method at dispatch
- a bounded read-only HTTP API over Notes and Glossary: node lookup, a note
  reading context, node, content, and glossary search, random node, relations,
  glossary terms, definitions, and due selection, and a hop-bounded
  neighborhood
- a SolidJS reading client with URL-as-state navigation, an Org reading column
  with a near/far spine, glance/pin/go navigation, a search-first entry
  surface, and a glossary dictionary with peek and an inert study trail
- a `slipbox web` command that embeds the built client behind a build feature,
  serves it with an SPA fallback, binds localhost only, and self-spawns the
  read-only daemon
- CI that builds and tests the reading client, and user documentation for the
  reading surface

Exit signal:

- note-content search ships as a parallel path with its own index and ranked,
  snippet-bearing contract, and node search, `node_fts`, and the Emacs recall
  path are byte-for-byte unchanged
- the web surface serves Notes and Glossary read-only, and no HTTP path can
  reach a mutating operation
- the reading client builds and tests in CI and is documented for ordinary
  users
- the introduced surface stays bounded: read-only, localhost-only, single
  user, no second database, no separate sync mechanism, no SSE or websocket
  push, and no MCP surface
- no new public bucket is added; the web reader is a third front-end over the
  same daemon-owned model, and Explorations, Reviews, and Assets get no web
  surface
- spaced-repetition grade writeback and any global or force-directed graph
  remain deferred

* 1.0.x: Stability Line

Theme: make the public surface dependable enough for ordinary users,
packagers, and scripts.

Focus:

- stable public JSON and durable record compatibility policy
- documented upgrade and rebuild behavior
- reliable release binaries and source builds
- benchmark gates that cover everyday, exploratory, review, asset, and
  structural paths
- cleaned module boundaries that allow ordinary maintenance without rescue
  refactors
- complete user-facing documentation and command help

Exit signal:

- one full release cycle passes with the public contracts holding steady
- bundled and system-SQLite build paths are verified in release automation
- compatibility-sensitive changes have explicit migration guidance
- the project can evolve through modules instead of monolith pressure
